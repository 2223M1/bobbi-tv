## 3. G01 / P1：退出所有权没有覆盖所有仍在执行的消费者

### 3.1 标准播放的线程先于任务实际结束返回

位置：

- `addons/script.module.bobbi.platform/lib/bobbi_platform/standard_session.py:196-200`：close仅join 0.1秒。
- `addons/plugin.video.bobbi/lib/services/standard_playback.py:36-38,285-290`：history仅join 0.3秒，subtitle仅join 0.1秒。
- `addons/plugin.video.bobbi/lib/portable_runtime.py`：标准close后进入host.close。
- `addons/script.module.bobbi.platform/lib/bobbi_platform/host.py:346-385`：宿主知道engine/catalog等，但不知道上述标准线程；最后释放runtime lease。

PR把HTTP处理器改为非daemon并在server_close等待，也把engine/catalog/preparation的等待改为排空。这些是有效措施，但它们没有自动覆盖标准适配器创建的下一集、字幕和历史写入线程。

独立实执行：真实StandardPlayback/StandardSession/HistoryWriter、真实threading.Event/Thread、真实InstanceLock OS文件锁，以及原样Host.close方法；provider/Kodi/其它宿主IO为替身。让已接收的任务暂时不返回，在产品close超时之后尝试取得相同锁。

| 任务 | close返回时旧任务仍运行 | 新安装者可取得同一锁 |
|---|---:|---:|
| 下一集发现/解析 | 是 | 是 |
| 中文字幕发现 | 是 | 是 |
| 观看历史写入 | 是 | 是 |
| 无后台任务控制 | 否 | 是（正确） |

这证明当前替换许可与真实消费者生命周期不一致，不证明已在盒子发生代码混代或数据库损坏。没有执行真实目录覆盖或模拟电视断电。任务尊重取消但仍在一个有限IO操作内，也可能超过0.1/0.3秒；“设置取消事件”不等于任务已经退出。

### 3.2 清理异常也会放行尚未排空的其它任务

同一Host.close在`try`中依次close图片、准备、分享和后台worker，`finally`无条件释放lease。若前面的images.close抛错，后面的catalog线程尚未join，finally仍释放锁。独立故障注入中：OSError已抛出、真实catalog worker仍存活，但另一InstanceLock取得成功。

这不是要求任何清理异常都永远卡死系统。正确规则是：一次清理失败不能跳过其他消费者排空；锁释放的依据是所有相关消费者确已结束，而不是“close函数已返回/异常退出”。错误应保留，后续可以在真实进程退出后由OS释放锁并恢复。

### 修复方向和放行条件

把标准路径与宿主的工作线程纳入同一关闭责任范围，先停止接收、取消/唤醒、逐项收集退出结果，最后才交出文件替换权。单个清理异常不能短路剩余排空。保留安装器15秒有界等待；等不完就不替换，不用扩大安装等待或强杀不相关进程制造通过。

测试应覆盖每类消费者慢返回、取消延迟、关闭异常，以及多个消费者同时存在；验证真实OS锁在所有消费者退出前一直不可取得。完整shutdown经过portable_runtime和真实host/runtime的候选组合也要补测。不能只把一个`.join(.1)`换成无界join就宣布所有路径关闭。

## 5. G03 / P3建议：条件性字段清空，不作为合并阻断

位置：`source_select.py:844-847`。renderer复用ListItem时，seeders/peers仅在真值且非cached时写入；若直接向该函数提供同key从10/5变成0/0或cached的更新，旧10/5会残留。正值变成7/8的控制则通过。

但完整链中`SourceListSession.publish`使用setdefault保留第一份同key数据。本轮又用真实session证实：第二份0/0/cached并不会覆盖第一份数据。因此尚未证明当前普通provider更新会触发上述renderer输入。将其降为条件性代码加固，而不是已证实的日常界面故障，更不能说实际BT速度错误。

包内四行参考补丁显式清空不适用字段，方法级测试可通过。它可以顺手做，但不是要求重构选源池，也不是阻止朋友内测的独立理由。
