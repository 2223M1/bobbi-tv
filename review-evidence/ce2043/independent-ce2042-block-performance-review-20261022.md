# CE2042 普通8 MiB / 显式1 MiB：四轮实机性能独审

## 判定

**1 MiB起步对这个文件的开播时间有两次一致改善，但不足以立即改为普通默认。** 两次候选都较各自前一对照更早AV；然而第二次候选在片时4.385秒发生约6.4–7.6秒缓冲，而其前一8 MiB对照没有观察到缓冲，45秒窗口内实际观看推进反而少5.137秒。它是有价值、但尚未收口的性能候选，不是“已经不卡”。

本轮不同于前一组open_range实验：这次已从真实日志证明A确实使用8 MiB完整块、B确实使用1 MiB完整块；B未碰到60秒诊断寿命。不存在“测错路线”或“到期造成卡顿”的证据。

不建议把该候选当整轮交付硬门槛。若最小后续实播仍出现类似倒退，保留普通8 MiB默认，交付其他已证修复，继续记录这个待优化问题，不以更早第一帧冒充完整收益。

## 路线、实例和可比性核验

- 四轮工具revision8，state completed，原生播放器前后均 `8bb2a99e2154432a4403ac55a81e3c253d7ab74f0e15369b85085f1a8bf4fd14`。
- 物理文件均 `689f58d95ad86c97edd0b8c83747f5861fbff4910abed2e7c8ec4b50ce111e57`，55,082,330,412字节。不同transport/request/native instance正确分组，没有把loopback URL不同误判为视频不同。
- scoped logs请求/transport/native实例与结果匹配，四组采集均无截断。
- A首GET和主GET的 `first_block_bytes=8388608`、stage=headers，初始主流fetch序列8/8/16/32/64 MiB；B对应1048576和1/1/2/4/8/16/32/64 MiB。没有progressive queue/producer指标混入。
- B的diagnostic_mode固定block_startup_1m，60秒。注册在resolve调用内；取**最早可能注册时刻resolve_began**至该transport所有日志最后事件，是寿命的保守上界：B1 **46.489秒**，B2 **46.000秒**，距离到期至少**13.511/14.000秒**。二者结束为本次精确Stop，不是到期。
- 四组均 `post_command_scoped_terminal_stop`、STOP、user_intent unchanged，非先有终态或错实例停止。
- 设置相同、前后不变，观察用户文件不变。四组均3840×2160、8声道stream metadata；passthrough=false，不能把此试验认证为透传音效验收。没有自动外部字幕搜索，不是普通手动选源的全链路认证。

## 能证明与不能证明

**能证明：**减小起步块明显减少了容器探测阶段的读入浪费：两个0偏移GET从各8MiB变为各约1MiB，主顺流更早开始；该候选在这两个窗口里都更早进入AV。这与“先少量交付、避免为短探测读完整大块”的设计动机一致。

**不能证明：**同样的1MiB floor还让主顺流增长多经过1/1/2/4几个阶段，新增连接/等待可能影响暖缓存；B2确实更早AV却更晚推进。不能仅凭本轮确定其卡顿完全由新增连接导致，因为CDN速度、系统负载和内容瞬时码率仍有波动，A1本身也停顿。更不能用A/B平均值掩盖B2对A2的可见倒退。

四轮本地下游都观察到4个GET；这是Kodi向ShareStream的请求数，**不是上游CDN连接总数**。块观测只覆盖初始增长及最终汇总；超过首64MiB后不逐块记录，所以即使suppressed=0也不能把8/13/8/12个fetch_end当全程请求次数。源码和初始日志能证明主顺流到64MiB候选多3次fetch，但不能从这份观测计算全片TLS次数。

当前候选优化仍只动一个floor，没有使用bound_guard或microbatch、没有改音画质量、解码器、缓存上限。没有理由通过放大缓存、降码率、关闭字幕或取消身份守卫来凑通过。

## 进入普通默认前的最小边界

1. **先解决证据中的混合结果，而非再无限重复同一45秒试验。** 明确以“首分钟实际推进/缓存停顿不倒退”为主要成功指标；首字节/AV只作为辅助。若B2式结果重现，维持8MiB默认。可以另研究“仅缩短探测起步而减少主流额外连接”的单变量候选，但不是本报告已验证方案，不应和当前floor改动一起叠加。
2. 如果继续推进1MiB普通候选，使用正常生命周期的同代受控候选验证，不把60秒诊断寿命直接带进普通播放，也不能把延长诊断当作已通过。先同文件持续至少约3分钟跨过60秒，执行一次中段seek及返回，再停止，确认没有反复buffer/拒绝/错误Stop。普通候选是否仅去掉诊断寿命还是又改默认，必须有明确diff并回归账号与Range边界。
3. 再抽此前未测的一部高码率电影和一部动漫，通过正常选源入口验证。涵盖容器头/尾读取差异、旁挂中文字幕/字体（正常后台流程）、原声优先和手动Off/延迟；不能拿这四次无外部字幕的诊断当完整日常验收。
4. 同代保存程序回退路径，保持原码流、当前账号、文件/实例绑定和续签。不需要把所有运营商/所有影片认证作为本次门槛，但也不能把单文件短窗包装成“所有115已秒开”。

在上述边界未收口前，可保留已测显式候选作为维护工具，**不建议无条件将普通STARTUP_SEGMENT_BYTES改成1MiB**。本轮其他已通过的正确性修复可以正常交付，不需被这项未证性能收益无限阻塞。
