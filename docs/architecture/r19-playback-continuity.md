# R19 播放后端：选中的源、文件进度和读取恢复

本次从 `f03c357` 分支修改播放后端。没有改皮肤、Kodi 内核、全局缓存或 CD2 配置。以下对照是源码职责和可复现的行为，不是竞品跑分或安装验收。

**续播。** 新目录记录要有完整来源指针，旧 MDsub 记录仅在原本没有该字段时走精确目录 URL 核验；指针损坏、来源不明或结果有歧义不回退到 BT。标准 Kodi 在片尾前只保留目录候选的身份，自然片尾再核验和解析，候选被换掉或手动停止都不打开后继文件。CoreELEC 原生保留原实例的一次性接续/手选授权；标准 Kodi 没有相同的自动弹窗保证。选源布局不变。

**115 读取。** 越界的 GET/HEAD 直接返回空体 `416` 和 `Content-Range: bytes */实际大小`，不找源站要地址。普通渐进流仍发有界 Range，ISO 仍可读到文件尾；都从已接收位置续读。重试按实际收到的字节计数：读满一个普通分段（原盘为 64 MiB）恢复预算，为并发读取让路不恢复预算。预算耗尽在已交付前缀处断开，不能补 HTML、重复字节或假装到达片尾。

**验证边界。** 本机回归覆盖同名同大小的异源、旧历史和损坏指针、暂停期间更换候选、自然片尾与 Stop、跨实例进度，以及独立数据库读回暂停及倒退后的进度。对应测试见 `test_catalog_playback_continuity.py`、`test_ce2029_lifecycle_audit.py`、`test_ce2096_pan_playback.py`、`test_native_history_coalescing.py`、`test_standard_file_history_close.py` 和 `test_ce_progressive_http.py`。

在同一台 AM6B 的独立 Python 进程内，以已安装读取器（`cabc8d23ec38…`）与候选（`cde4c8e2096d…`）逐一驱动实际 CoreELEC curl，通过回环 HTTP 读取生成的 393,216 字节：

- 普通 MKV 区间、ISO 开尾、ISO 后缀均逐字节一致；两种越界请求只有候选都返回正确总长。
- 每个 64 KiB 分段短读一次，两版均用 12 次源请求完整读回。最初候选过早中断，已修正后重测。
- 同一逻辑分段内交替注入空响应和读锁让行：已装版用 44 次请求读完，候选达到第 4 次失败后停止（共 7 次请求）。已交付的前缀逐字节正确，未伪报完整成功。这验证重试上限，不代表网络更快。

同机另一个隔离进程读取盒上实际 MDsub 目录（`b44a041fcfd3…`），选取其中确实相邻的两集，再加入一个文件名、大小、季集都相同的异源索引项。已装版选中了注入的副本；候选保留原目录文件，预查零次播放解析、最终一次，替换预约不解析。对同一组模拟播放时钟，停止前已装版只报告起始 3 秒；候选额外报告暂停时的 5 秒、恢复后的 50 秒和倒退后的 7 秒，同位置暂停 30 分钟没有重复报告。这项检查屏蔽了网络和文件写入，使用测试开关、账号与内存回执，不是盒上 Kodi 播放或磁盘历史验收。

没有修改盒上插件或用户数据；探针前后 Kodi 进程未变。此次未用真实 115 账号/CDN 做同片 A/B，未实测 Android，也不代表暂停半小时就应预载半小时内容。已装 R19 的真实 115 ISO、MKV 播放记录单列在[既有验收](r19-glass.md)，不能归作本次候选的成绩。
