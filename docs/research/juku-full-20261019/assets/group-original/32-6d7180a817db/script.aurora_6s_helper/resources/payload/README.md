# 修复数据布局

按 `分支/机型/无线芯片` 分类。6S 只有 RTL8852 版本，因此不再增加芯片层。

```text
payload/
├── ng/
│   ├── 6s/                 # DTB、Realtek 配置、驱动和 systemd 加载文件
│   └── 4pro/
│       ├── ap6275p/        # 专用 DTB、灯条驱动和 LED 服务；无线用系统自带支持
│       └── rtl8852/        # 6S 同方案，4 Pro 名称/标识的 DTB 和加载脚本
├── no/
│   ├── 6s/                 # DTB、Realtek 配置、V12 规则
│   └── 4pro/
│       ├── ap6275p/        # 实机验证通过的 DTB、V12 规则
│       └── rtl8852/        # 6S 同方案，4 Pro 名称/标识的 DTB
└── hashes.json             # 相对于 payload 的完整文件路径与 SHA256
```

安装器按分支、机型、芯片选择对应目录。优先使用原厂 Android 型号区分机型，
A4111 / rev D 保留实物机型选择；当前 DTB 名称不能证明实物机型。
无线芯片优先采用已识别的 PCI ID（包括 rev B 配 RTL8852 的 4 Pro）；未识别到已知
PCI 芯片时，4 Pro 才按 CPU 修订号推测：rev A/B/C 为 AP6275P，rev D 为 RTL8852。
A4112 使用 6S 包，仅提供 RTL8852 组合，不将实际博通芯片当作 RTL8852 部署。
无原厂机型时支持手动确认机型；未知 CPU 修订且无可用 PCI ID 时，不猜测 4 Pro 的无线版本。

NG 与 NO 各 RTL8852 包的蓝牙配置分别存放，当前内容相同。发布前应同步更新 `hashes.json`。
机型数据不交叉回退：缺少某组合时不能借用另一型号的 DTB、驱动或蓝牙配置。
盒子上的安装路径、NG 服务名及服务独立于 Kodi 的启动方式保持原样。
所有 NO 包均部署相同的 V12 键盘分类规则，NG 不部署。
新备份使用格式 5，记录机型、芯片和清理文件；安装器仍可恢复格式 1/2/3/4 的旧备份。
格式 3 的 AP6275P 备份只恢复 DTB，不修改当时未纳入备份的 V12 规则。
4 Pro RTL8852 的 DTB 与对应 6S 版仅 model/coreelec-dt-id 不同；其硬件运行效果尚待实机验证。

AP6275P NG 部署会备份并删除已知旧 RTL8852 NG 模块、蓝牙配置和 Wi-Fi 服务文件，
移除旧 Wi-Fi/Realtek 蓝牙强制启动链接，并停用已存在的 bt-uart-keepalive 服务。
共享灯控驱动、加载脚本和 LED 服务替换为本型号版本。内核中已加载的驱动在重启后切换，
不在安装中强制卸载；清理不递归删除目录，不改系统自带驱动/固件。

NO 自 1.6.1 起三套 DTB 默认增加 `mmc-hs400-1_8v`、设置 `tx_delay=16`，
各自的 `coreelec-dt-id` 追加 `_hs400`，不与官方 DTB 使用相同标识。
NG DTB 和标识不变。灯控仍接受旧 NO 标识，兼容仅升级插件的机器。
当前 HS400 实机读写验证来自 4 Pro/AP6275P；6S、4 Pro/RTL8852 的这一默认值
尚未完成各自实机稳定性验证。修改的是插件内的修复素材，不会由 Kodi 服务自动安装。
